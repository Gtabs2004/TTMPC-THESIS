## Project Overview

REGANT is a web-based Decision Support System (DSS) for the Tubungan Teachers' Multi-Purpose Cooperative (TTMPC). It combines cooperative operations management (loans, savings, membership) with ML-driven analytics (credit risk scoring, loan demand forecasting, MIGS scoring).

## Commands

### Frontend (inside `TTMPC_THESIS/`)
```bash
npm run dev       # Start dev server at http://localhost:5173
npm run build     # Production build → dist/
npm run preview   # Preview production build
npm run lint      # ESLint
```

### Backend (FastAPI, inside `TTMPC_THESIS/src/server/`)
```bash
uvicorn main:app --reload --host 127.0.0.1 --port 8000
```
Dependencies: `pip install -r requirements.txt` (Python 3.13, use `.venv/`)

### Environment
Frontend requires a `.env` in `TTMPC_THESIS/` with:
- `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`
- `VITE_API_BASE_URL=http://127.0.0.1:8000`
- Resend API key for email notifications

## Architecture

### Role-Based Access Control
The app has 8+ distinct user roles, each with its own portal and route namespace:
- **Member** — self-service (loans, savings, profile)
- **Cashier** — transaction recording (deposits, withdrawals, payments, disbursements)
- **Bookkeeper** — loan evaluation, MIGS scoring, ledger management, POS
- **Manager** — loan approval review
- **Treasurer** — disbursement, accounting, payment reconciliation
- **BOD** (Board of Directors) — member approval, policy setting, secretary functions
- **Non-member/KOICA** — limited loan access for non-members

All 150+ routes are defined in `src/Router.jsx`. Auth context (`src/contex/AuthContext.jsx`) stores role, membership ID, and session state. Note: the context directory is spelled `contex` (not `contexts`).

### Data Flow
- **Database:** Supabase (PostgreSQL) with Row-Level Security enforced per role
- **Auth:** Supabase Auth with `sessionStorage` (not `localStorage`) for multi-tab isolation
- **Frontend → DB:** Direct Supabase client calls (`src/supabaseClient.js`) for most CRUD
- **Frontend → Backend:** FastAPI at port 8000 for ML inference, loan computation, and email

### ML/Analytics Backend (`src/server/`)
Note: `main.py` now exposes all backend routes under an `/api/...` prefix (loans, cashier, treasurer, bookkeeper, admin, account, audit-log, etc. — 80+ endpoints). The three analytical engines below are the ML-specific slice of that:

1. **Credit Risk (`risk_model.py` + `risk_features.py`)** — model bundle `models/ttmpc_risk_model.pkl` (the older `ttmpc_credit_risk_model.pkl` is a superseded artifact, kept on disk but no longer loaded)
   - Endpoints: `GET /api/risk/model-info` (thresholds/metrics the UI reads instead of hardcoding), `POST /api/risk/predict`, `GET /api/credit-risk/queue`
   - `FEATURE_COLUMNS` (in `risk_model.py`) is the current canonical feature list — e.g. `LoanAmount`, `Term`, `MonthlyDue`, `Dependents`, `OccTier`, `Age`, prior-loan behavior fields (`PriorLoans`, `PriorRefinances`, `PriorBehind`, `PriorRestructured`, `PriorPenalties`, `PriorBorrowed`, `DebtGrowth`, `MonthsSinceLastLoan`, `ConcurrentLoans`), and account signals (`ShareCapital`, `Savings`, `HasTimeDeposit`, `SavingsChange`, `Groceries`, `HasSnapshot`) — this replaced the old `Stability_Score`/`Repayment_Stress_Index`-style feature set; verify against the file before assuming any specific field name still applies.
   - Displayed in `src/components/CreditRisk/CreditRiskPage.jsx`

2. **Loan Demand Forecasting (`demand_model.py`)** — SARIMAX models per loan type (`models/consolidated_model.pkl`, `models/emergency_model.pkl`, ~7 MB each)
   - Endpoints: `GET /api/analytics/demand/forecast`, `GET /api/analytics/demand/actuals`
   - Output: 12-month forecast with 80% confidence intervals
   - Displayed in `src/components/LoanDemandForecastCard.jsx`

3. **MIGS Scoring (`migs_engine.py`)** — Pure function, no DB calls
   - 7 scoring criteria totaling 100 points; threshold 50 (`MIGS_THRESHOLD`) = MIGS classification
   - Loan multiplier: 5× (MIGS) vs 3× (Non-MIGS) — `MIGS_LOAN_MULTIPLIER` / `NON_MIGS_LOAN_MULTIPLIER`
   - Endpoints: `GET /api/migs/members`, `POST /api/migs/recompute-all`, `GET /api/migs/label/{member_key}`, `GET /api/migs/members/{member_key}`
   - Used by Bookkeeper portal `src/Bookkeeper/Components/MIGS.jsx`

### Loan Lifecycle
Applications flow through roles in sequence:
1. Member applies via `src/LOANFORMS/` → submitted to DB
2. Bookkeeper evaluates & performs MIGS scoring
3. Manager reviews and approves/rejects
4. Treasurer disburses funds
5. Cashier records payments

Loan types: Consolidated, Bonus, Emergency (member), and KOICA (non-member).

### ISC (Interest on Share Capital) Distribution
Annual dividend feature: a bookkeeper-chosen basis period (average share capital over a month range, cannot start before December 2025) generates a payout that is either capitalised into a member's share capital or paid as cash.
- **Frontend:** `src/Bookkeeper/Components/ISC_Distribution.jsx` (route `/bookkeeper-isc` — calculate/post) and `ISC_Journal.jsx` (route `/bookkeeper-isc-journal` — posting history/reversal). `IscPayoutPreferencesModal.jsx` is the March General Assembly step — the **only** place a member's share capital actually changes for a posting; unchecking a member there marks them for cash instead of capitalisation (default is capitalise).
- **Backend:** all logic lives in Postgres RPCs (`isc_calculate_preview()`, `isc_post()`, `isc_reverse()`, `isc_settle_posting()`), not FastAPI — the app calls them via `supabase.rpc(...)`. `isc_post()` only ever records a payable; `isc_settle_posting()` is what moves capital or marks a cash payout.
- **Schema/migrations:** `src/server/isc_v2_01_schema.sql` through `isc_v2_06_allow_historical_years.sql` are the current, applied migration chain (each is incremental — apply in order), plus point fixes `isc_fix_double_reversal.sql`, `isc_fix_posted_by_fk.sql`, `isc_fix_stale_balance.sql`. The original `isc_dividend_schema.sql` is superseded by the v2 chain; don't reapply it. `src/server/isc_checks/*.sql` are ad-hoc verification queries, not migrations.
- Design rationale (segregation of duties: bookkeeper posts, only Manager reverses and never their own posting; exclusion-constraint overlap prevention; rounding rules) is in `ISC_DIVIDEND_PLAN.md` at the repo root — read it before changing ISC behavior.

### 6-Month Renewal Rule Override
A member with an active loan can't renew until 6 monthly payments are recorded (`RENEWAL_MIN_PAYMENTS`). For urgent need they can request an override; the Bookkeeper approves or rejects it; approval unlocks Renewal for that one loan for 30 days or until spent on a renewal application.
- **Table/migration:** `src/server/loan_renewal_override_schema.sql` (`loan_renewal_override_requests`) — must be applied in Supabase. Rows are never deleted; it is the history ledger. RLS is on with no client policies: all access goes through FastAPI on the service-role key.
- **Backend:** "6-Month Renewal Rule Override" section of `main.py` (`/api/member/renewal-override*`, `/api/bookkeeper/renewal-override-requests*`). Identity comes from the verified JWT, never the body; a Bookkeeper can't review their own request. State changes are mirrored into `audit_log` (`entity_type='loan'`, `context.kind='renewal_override'`) and the `loan_notifications` bell feed.
- **Frontend:** member request UI is in `Member_ApplyLoans.jsx` + `RenewalOverrideModal.jsx`; Bookkeeper queue/history is `Bookkeeper/Components/Renewal_Overrides.jsx` (`/bookkeeper-renewal-overrides`). `useLoanEligibility` layers approved overrides onto the `get_loan_eligibility` RPC result (`can_renew`, `override_applied`); the loan forms' `sixMonthsPaid` gate honors it. `submitUnifiedLoan` calls `/consume` after a renewal so one approval can't be reused.
- The override waives the 6-month rule only — not the Bonus May/November window, and it does not pretend payments were made (the existing balance is still deducted in full).

### Email Notifications
Sent via Resend API through FastAPI endpoints (`/api/send-status-email`, `/api/loans/notifications/dispatch`, `/api/loans/notifications/member`, `/api/loans/email/dispatch`). Templates in `src/server/services/loan_email_templates.py`.

### Database Schema
SQL schema files live in `src/server/*.sql`. Key triggers:
- CBU auto-sync from loan disbursements (`cbu_sync_from_loan_disbursement_include_emergency.sql` is the current version)
- Audit trail for all member/loan modifications

Migration scripts are in `src/server/migration/` — these are one-off data migration utilities, not part of normal app operation.
