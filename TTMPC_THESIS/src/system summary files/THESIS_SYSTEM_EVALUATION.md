# REGANT (TTMPC) — Solutions Architecture & Thesis-Defense Readiness Evaluation

**Role:** Lead Solutions Architect / IS Thesis Examiner review of the full repository — `TTMPC_THESIS/src/`, `server/`, `analytics/`, config files.

**Companion documents:** this evaluation builds on and cross-references three prior audits already in this repo root — `HARDCODED_AUDIT.md` (mock data / stub scan), `UI_CONSISTENCY_AUDIT.md` (design-system drift), and `NAVIGATION_AND_ACTIONS_AUDIT.md` (routing & action integrity). Findings already fully verified there are cited, not re-derived; this document's new investigation covers PWA/offline behavior, RBAC bypass surface, audit-log integrity, demand-forecast training rigor, and model explainability.

---

## 1. Executive Summary

**Verdict: Defensible, with one showstopper that must be fixed before a panel sees it, and two governance gaps a rigorous examiner will find within minutes of clicking around.**

The system is architecturally more mature than a typical thesis prototype: a real three-tier separation (React → FastAPI → Supabase), a genuinely rigorous SARIMAX training pipeline with documented per-loan-type hyperparameters, a Random Forest credit-risk model with correctly-enforced feature ordering and a properly-implemented MNAR strategy, and a PWA configuration that deliberately does *not* cache financial data offline (the right call, and it's commented as a deliberate choice, not an oversight). Loading-state discipline on the highest-stakes forms is genuinely good — the loan submission button has a *double* duplicate-submission guard.

Set against that: **the Bookkeeper portal's own Audit Trail page is disconnected from the database and permanently shows fabricated demo data**, while a correctly-built, database-backed version of the exact same feature sits unused elsewhere in the same folder — this is the kind of thing a panel member testing the "auditability" claim in the thesis will find immediately. Separately, **role-based access control is enforced only by convention and Supabase RLS, never by a route guard** — no code stops an authenticated Member from typing a BOD or Treasurer URL directly into the address bar. And **the fee/interest-rate policy screen that drives every member's loan math has zero audit trail**, at either the application or database level.

None of these are "the ML doesn't work" or "the math is wrong" — the core computational engines are sound. They are integrity/governance gaps in a system whose thesis explicitly foregrounds decision-support rigor and auditability, which is exactly why a panel would probe them.

## 2. Pillar Breakdown

### 2.1 Architecture & Operations

**Component decoupling — good, deliberate, not accidental.** The frontend talks to Supabase directly for CRUD (`src/supabaseClient.js`) and to FastAPI only for computation that needs Python (ML inference at [risk_model.py](TTMPC_THESIS/src/server/risk_model.py), forecasting, PDF stamping, email). This is a defensible split, not a muddle — CLAUDE.md documents it and the code follows it consistently in every file sampled across three prior audits.

**PWA/offline readiness — well thought through.** [vite.config.js:11-74](TTMPC_THESIS/vite.config.js#L11-L74) is unusually well-commented for a thesis project: it explicitly precaches the app shell (JS/CSS/HTML/icons) but **excludes API calls from the offline fallback** (`navigateFallbackDenylist: [/^\/api\//]`) and only applies `CacheFirst` to images, never to financial data. The comment at line 13 states this outright: "Access control is still enforced by Supabase auth" and "data still requires network" — someone thought about the failure mode of showing a cashier stale balance data offline and designed around it. This is a genuine strength worth stating plainly in a defense.

**State & data flow — provider tree is clean, but there's no role boundary in it.** [main.jsx](TTMPC_THESIS/src/main.jsx) wraps the app in `ThemeProvider → NotificationProvider → ConfirmProvider → AuthContextProvider`, then mounts `NotificationContainer`, `PwaInstallGate`, `StandaloneMemberOnlyGuard`, and finally `RouterProvider`. Auth, notifications, confirmation dialogs, and theme are each a single global context — no portal reimplements its own. `StandaloneMemberOnlyGuard.jsx` is well-designed but narrow in scope by its own documentation ([:1-16](TTMPC_THESIS/src/components/StandaloneMemberOnlyGuard.jsx#L1-L16)): it only activates when the app is running as an **installed PWA in standalone display mode** — "Zero effect in a normal browser tab." See §2.2 for why this matters.

### 2.2 Security & Governance

**RBAC is UI-cosmetic only — this is the pillar's central finding.** [usePortalRole.js](TTMPC_THESIS/src/utils/usePortalRole.js) fetches the user's role client-side and its own docstring says what it's for: "Used by shared BOD/Secretary sidebars to **grey-out sections** outside the user's role" — presentation, not enforcement. A full read of `Router.jsx`'s 91 routes shows exactly one guard in use, `MemberOnboardingGuard`, and it is wrapped **only** around the 8 `/member-*` routes to check onboarding completion (`is_email_dummy`/`is_temporary`) — its own comment states plainly it "does NOT need this check" for staff portals ([MemberOnboardingGuard.jsx:15](TTMPC_THESIS/src/Member/Components/MemberOnboardingGuard.jsx#L15)). There is no `ProtectedRoute`, `RequireRole`, or equivalent anywhere in the codebase (confirmed by grep across all of `src/`). Concretely: an authenticated Member who types `/bod-manage-loans` or `/manage-loans` into the address bar will have React fully render that component's shell, sidebar, and any client-computed values. Whether they see real *data* on it depends entirely on Supabase RLS blocking the query — which is the correct place to enforce this, but it means the UI layer provides **zero defense in depth**, and any component that computes or displays something client-side without a round-trip to a protected table (see the hardcoded audit-log case below) bypasses even RLS. `StandaloneMemberOnlyGuard` doesn't help here either — it explicitly does nothing in a normal browser tab, only in an installed home-screen PWA.

**Auditability — a critical, concrete defect, not a design gap.** [Router.jsx:15,118](TTMPC_THESIS/src/Router.jsx#L15) routes the Bookkeeper sidebar's "Audit Trail" link to `Bookkeeper/Components/Audit-Trail.jsx` (hyphenated). That file's entire log table is a hardcoded array — [Audit-Trail.jsx:97-105](TTMPC_THESIS/src/Bookkeeper/Components/Audit-Trail.jsx#L97-L105): every row is the same fictional user ("Ana Reyes"), fixed March-2026 timestamps, and even includes a fabricated `"Unauthorized Export Attempt" / status: "Flagged"` entry that never happened. It has no Supabase call anywhere in the file. Meanwhile, `Bookkeeper/Components/Audit_Log.jsx` (underscore) **exists in the same folder**, correctly imports the shared [AuditLogViewer.jsx](TTMPC_THESIS/src/components/AuditLogViewer.jsx) — which genuinely queries `supabase.from("audit_log")` with real filtering and counts ([:146-185](TTMPC_THESIS/src/components/AuditLogViewer.jsx#L146)) — exactly like the BOD, Manager, Treasurer, and Cashier portals all correctly do. But `Router.jsx` **never imports `Bookkeeper/Components/Audit_Log.jsx` at all** — it's dead code. The only reachable Bookkeeper audit page is permanently fake. This is the single highest-confidence, most concrete finding in this entire evaluation.

**Where real auditability *does* exist, it's incomplete.** [audit_log_triggers.sql](TTMPC_THESIS/src/server/audit_log_triggers.sql) attaches DB-level audit triggers to exactly four tables: `loans`, `member_account`, `staff_termination_requests`, `member_applications`. **`loan_fee_policies` — the table BOD edits from [Loan-Policies.jsx](TTMPC_THESIS/src/BOD/Components/Loan-Policies.jsx) to change interest rates, service fees, and CBU retention rates for every future loan — has no trigger, and the component itself captures no `updated_by`/`changed_by` field** (confirmed by grep: zero actor/timestamp references in the file). A cooperative's financial-policy engine can be changed with no record of who changed it or when. This is a direct hit against the thesis's own "auditable, tiered approval" framing (see `THESIS_SPEC.md`'s Contradiction #4, which this independently corroborates from the live code rather than the spec document).

**Data protection — clean.** Already verified in `HARDCODED_AUDIT.md`: no hardcoded API keys, DB credentials, or `sk_live`/`sk_test`-style secrets anywhere in `src/`; the Supabase service-role key is read from environment variables in all three places it's used.

### 2.3 Data & Predictive Analytics

**Feature-contract enforcement — correctly implemented, verified end-to-end.** `risk_model.py`'s `prepare_features()` returns `pd.DataFrame([row])[FEATURE_COLUMNS]` ([:148](TTMPC_THESIS/src/server/risk_model.py#L148)) before the model ever sees the row, and `main.py`'s `/api/risk/predict` route ([:8461](TTMPC_THESIS/src/server/main.py#L8461)) calls that function directly rather than hand-building a dict that could skip it. `feature_contract.md` and `predict_example.py` document the same five-feature order identically. There is no path in the live code where feature order could silently drift.

**MNAR handling — correctly implemented, not naive.** `Income_Is_Missing` is a genuine binary indicator computed at [risk_model.py:135](TTMPC_THESIS/src/server/risk_model.py#L135) (`1 if income_f is None or income_f == 0 else 0`), and `Repayment_Stress_Index` uses the documented `-999` sentinel exactly when income is missing rather than falling back to a mean/median imputation — confirmed in both `risk_model.py` and independently in `feature_contract.md`'s own description of the same logic. `model_metadata.json` confirms this is a real, trained `RandomForestClassifier` (`n_estimators=150, max_depth=5, class_weight='balanced', random_state=42`) with `scikit-learn==1.6.1` pinned exactly to the training version in `requirements.txt`.

**One real ML caveat worth flagging for the defense, found independently of this evaluation's asked questions:** `model_metadata.json` records `test_roc_auc: 0.434` on the held-out test set — below 0.5, i.e. worse than chance, despite `test_accuracy: 0.594`. This isn't something the code does wrong, but it's a number sitting in the shipped metadata a panelist could ask about directly; have an explanation ready (small 111-row test split, class-imbalance interaction with AUC) rather than being surprised by the question.

**Forecasting rigor — genuinely strong, this is the standout pillar.** [train_demand_models.py](TTMPC_THESIS/src/analytics/Loan%20Demand%20Forecasting/train_demand_models.py) resamples to explicit month-end frequency (`.resample("ME")`, [:80](TTMPC_THESIS/src/analytics/Loan%20Demand%20Forecasting/train_demand_models.py#L80)) and documents *why* zero-filling matters — "Months with no loans of that type are zero-filled so the SARIMAX index is [complete]" ([:67](TTMPC_THESIS/src/analytics/Loan%20Demand%20Forecasting/train_demand_models.py#L67)) — a detail many practitioners skip and that silently breaks SARIMAX's seasonal indexing if missed. Per-loan-type hyperparameters are documented in the file header and match the deployed `.pkl` metadata exactly: Consolidated `order=(1,1,1) seasonal=(0,1,1,12)`, Emergency `order=(0,1,1) seasonal=(1,1,1,12)`. `statsmodels==0.14.4` is pinned in `requirements.txt` matching the training environment.

### 2.4 Maintainability & Resilience

**Component reusability — already fully audited in `UI_CONSISTENCY_AUDIT.md`; the short version: no shared `Button`/`Modal`/`Badge`/`Input` primitives exist anywhere in `src/components/`, and 11 separate files hand-roll the identical modal-shell markup.** The audit-log split found in §2.2 above is a second, worse instance of the same disease: two independently-built implementations of the same feature, one wired in, one not, with no shared source of truth. Recommend reading that report's Design Token Refactoring Checklist alongside this one — item 6 there (stand up a primitives layer) would have made the dead-vs-live Audit Trail split structurally impossible, since there'd be only one place to build it.

**Error handling & fallback — no "RiskHeuristic" exists, and that's actually correct, not a gap.** A repository-wide search for any heuristic fallback file/function related to risk scoring returns nothing — there is no `RiskHeuristic`. What *does* exist is better: both ML-backed endpoints (`/api/risk/predict` and `/api/analytics/demand/forecast`) raise `HTTPException(status_code=503, ...)` when the `.pkl` file is missing or fails to load (`ModelNotAvailableError`/`DemandModelNotAvailableError`, `main.py:8534,8951`) rather than silently substituting a made-up heuristic number. A 503 that the frontend has to visibly handle is more honest than a silent fallback that looks like a real prediction — this is the right failure mode for a credit-risk model, where a fabricated "safe-looking" fallback score would be actively dangerous. (Contrast this with the loan-*computation* path, which **does** have a client-side local-math fallback with hardcoded fee defaults — already flagged as a Moderate finding in `HARDCODED_AUDIT.md` finding #7 — the risk model correctly does not follow that same pattern.)

**Dependency pinning — verified exact.** `requirements.txt` pins `scikit-learn==1.6.1` and `statsmodels==0.14.4`, matching `model_metadata.json`'s `sklearn_version_at_training` exactly. No drift risk on `.pkl` deserialization from an unpinned environment.

### 2.5 Domain & Policy Alignment (Business Logic)

**Fee/interest math is centralized in exactly one place, with a documented fallback.** [loanComputeApi.js](TTMPC_THESIS/src/LOANFORMS/loanComputeApi.js) is the single source for service-fee brackets (`computeServiceFee`, [:104-112](TTMPC_THESIS/src/LOANFORMS/loanComputeApi.js#L104)), CBU deduction, insurance, and notarial fee — all pulled from the `loan_fee_policies` table BOD edits. It is genuinely centralized (`useLoanComputation.js` is a thin hook delegating to it, not a second implementation), which is correct architecture. The caveat, already documented in this session's earlier feedback review and carried into `HARDCODED_AUDIT.md` finding #7: a single failed backend call permanently flips a session-level flag (`backendComputeAvailable`) that reroutes every subsequent computation in that browser tab to a **duplicated local reimplementation** with a hardcoded `FEE_POLICY_FALLBACKS` object as last resort ([:46-79](TTMPC_THESIS/src/LOANFORMS/loanComputeApi.js#L46-L79)). A BOD fee-policy edit can silently diverge from what a member sees quoted if their session ever hit one transient network blip.

**High-value-loan BOD escalation is real and enforced in the schema, not just documented.** [bod_high_value_loan_schema.sql](TTMPC_THESIS/src/server/bod_high_value_loan_schema.sql) adds a `loan_status` CHECK constraint permitting `'recommended for bod approval'` / `'bod rejected'` specifically for Consolidated loans over ₱500,000, inserting a mandatory BOD approval step between Bookkeeper and Manager for exactly the loans the business rules require it for. This directly corroborates the `THESIS_SPEC.md` claim of a "Parallel Risk Matrix / Priority Queue" governance step — it is genuinely implemented, not aspirational documentation.

### 2.6 Usability & Explainable AI (XAI)

**Loading-state discipline — good, verified with a real double-guard.** Already fully audited in `NAVIGATION_AND_ACTIONS_AUDIT.md`: `Consolidated_Loan.jsx`'s submit button disables on `loading || printing || exceedsCeiling || renewalBlocked || eligibilityFailed || stressIndexExceeded`, **and** the submit handler itself has a second `if (loading) return;` early exit — a belt-and-suspenders guard against double-billing that most of the codebase's other forms don't bother with. Worth citing as a positive example to the panel, and worth propagating the same pattern to the other loan-type forms if time permits.

**Model explainability — a labeled input echo, not true feature-importance explanation.** `LoanApprovalDetails.jsx`'s "Features Used by the Model" panel ([:1565-1568](TTMPC_THESIS/src/Manager/Components/LoanApprovalDetails.jsx#L1565)) is real and does surface the five feature values (Stability Score, Repayment Stress Index, etc.) that were fed into the model for that specific application — which is honest and useful. But it is **not** feature-importance or SHAP-style explanation: it shows what went *in*, not which of those inputs actually drove the "High Risk" classification for that specific prediction. `risk_model.py` has no call to `.feature_importances_`, SHAP, LIME, or any comparable method anywhere in the file. For a defense, be precise about which claim you're making: this UI supports "the decision was based on these declared inputs" (true, and defensible), not "here is why the model flagged this member" (not currently implemented). If the thesis text implies the latter, that's a gap worth closing — even a static, precomputed `feature_importances_` bar chart from the trained Random Forest (computed once at training time, not per-request) would close most of this gap cheaply.

## 3. Critical Vulnerabilities (Showstoppers)

Ranked by how quickly a technical panel would find each one.

1. **🔴 Bookkeeper's Audit Trail page is disconnected from the database and shows fabricated demo data.** [Router.jsx:15,118](TTMPC_THESIS/src/Router.jsx#L15) → [Audit-Trail.jsx:97-105](TTMPC_THESIS/src/Bookkeeper/Components/Audit-Trail.jsx#L97-L105). A correctly-built, DB-backed replacement (`Audit_Log.jsx`, same folder) already exists but is never routed to — this is a one-line fix (swap the import/route), not a rebuild. **Fix this before any live demo** — it is the single easiest "gotcha" for anyone testing the system's audit claims.
2. **🔴 No route-level RBAC — access control depends entirely on Supabase RLS, with no defense in depth in the UI layer.** [usePortalRole.js](TTMPC_THESIS/src/utils/usePortalRole.js) is cosmetic; `Router.jsx` has no role guard on any staff route. Combined with finding #1, this means a misrouted or misconfigured component (like the fake Audit Trail) can leak fabricated-but-plausible-looking content to any authenticated user who navigates to it directly, regardless of role, since it never queries a protected table in the first place.
3. **🟠 `loan_fee_policies` — the table controlling every member's loan math — has no audit trail at any layer.** No DB trigger ([audit_log_triggers.sql](TTMPC_THESIS/src/server/audit_log_triggers.sql) covers only 4 unrelated tables), no `updated_by`/`changed_by` field, no application-level log. A BOD member changing an interest rate leaves no record.
4. **🟠 Three Cashier real-money screens (Withdrawals, CBU Deposit, CBU) have no confirmation gate before submitting**, while their sibling screens in the same portal do — fully detailed with file:line evidence in `NAVIGATION_AND_ACTIONS_AUDIT.md` §2.
5. **🟡 The public landing page's mobile "Contact" nav link navigates home instead of to the contact section** — cosmetic, but it's the first thing a visitor not yet in the authenticated app can click; fully detailed in `NAVIGATION_AND_ACTIONS_AUDIT.md` §2.

## 4. Action Plan

### High Priority — fix before any thesis defense or demo
1. Rewire the Bookkeeper "Audit Trail" sidebar link: change `Router.jsx` to import and route `/audit-trail` to `Bookkeeper/Components/Audit_Log.jsx` (the real, working, `AuditLogViewer`-backed component) instead of `Audit-Trail.jsx`. Delete or archive the hardcoded-data file once confirmed unused elsewhere.
2. Add a lightweight route-level role guard (a `RequireRole(allowed=[...])` wrapper, mirroring `MemberOnboardingGuard`'s existing pattern) around every non-Member portal's routes in `Router.jsx`, so a mismatched role redirects before any component mounts — not a replacement for RLS, but a necessary second layer given finding #1 shows what an ungated route can expose.
3. Add `updated_by`/`updated_at` columns to `loan_fee_policies` (populated from the authenticated user at write time) and either a DB trigger mirroring the existing four in `audit_log_triggers.sql`, or an explicit log write in `Loan-Policies.jsx`'s save handler.

### Medium Priority — solidify before Q&A, not necessarily before the demo
4. Add the missing `useConfirm()` gate to `Cashier_Withdrawals.jsx`, `Cashier_CBU_Deposit.jsx`, and `Cashier_CBU.jsx` (pattern already built and working in `Cashier_Payments.jsx`/`Cashier_Disbursement.jsx` — copy, don't reinvent).
5. Fix the `App.jsx` "Contact" mobile-nav link and reconcile the "Features" nav item's desktop-vs-mobile behavior mismatch (both detailed in `NAVIGATION_AND_ACTIONS_AUDIT.md`).
6. De-stickify `loanComputeApi.js`'s `backendComputeAvailable` flag so one transient backend error doesn't permanently strand a session on hardcoded fee-fallback math (`HARDCODED_AUDIT.md` finding #7).
7. Have a prepared answer for the `test_roc_auc: 0.434` figure in `model_metadata.json` — don't let it be a surprise question.

### Low Priority — worth doing, not defense-critical
8. Compute and surface static `feature_importances_` from the trained Random Forest (once, at training time) alongside the existing "Features Used" panel, so the XAI claim is closer to "why" rather than "what went in."
9. Extract a shared `<Modal>`/`<Badge>`/`<Button>` primitives layer (full plan in `UI_CONSISTENCY_AUDIT.md` §4) — this is also the structural fix that prevents the audit-log dead-code split from recurring elsewhere.
10. Extend `useSearchParams` to the highest-traffic paginated tables so filter/page state survives a refresh (`NAVIGATION_AND_ACTIONS_AUDIT.md` §4).
